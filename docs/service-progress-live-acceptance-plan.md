## Actual default/fake/real status (do not conflate)

- Client unset/`TARKMAN_SERVICE_PROGRESS_PRODUCT=0` returns ordinary Expo config
  without loading the plugin; JS action requires iOS + `extra.serviceProgressProduct`
  + native module. `=1` generates **only the isolated QA identity**, requires explicit
  bare HTTPS `SERVICE_PROGRESS_DEVELOPMENT_ORIGIN` and
  `SERVICE_PROGRESS_DEVELOPMENT_READER_ORIGIN`, removes production associations/EAS
  updates, and deliberately adds **no team/profile/APNs entitlement**. Extension
  currently gets `CODE_SIGNING_ALLOWED=NO`. This is not a signed-device recipe.
- `TARKMAN_SERVICE_PROGRESS_SIMULATOR=1` additionally requires explicit loopback
  `SERVICE_PROGRESS_SIMULATOR_API_ORIGIN`; seals native origins to reserved `.invalid`
  names. Debug Simulator + isolated bundle checks gate the seam. Native verification,
  synthetic `aabb` registration and journal storage are in memory; Activity requests
  `pushType:nil`. It does not prove durable Keychain relaunch, token issuance or APNs.
- The actual non-fake configured caller already requests `.token`, stages durable
  recovery before observation/PUT, observes rotations and has explicit reconciliation.
  Do not commission another token bridge. Standalone generator's separate
  `SERVICE_PROGRESS_REMOTE_EXPERIMENT=1` selects its development entitlement; it
  does not make the integrated plugin generate that entitlement.
- Backend [normal factory source](<https://github.com/mattash/Tarkman/blob/46481161509155d04e3fcf60ce7928ea19f9614b/app/services/service_progress.rb>)
  still selects **FakeProvider only**, sandbox topic
  `org.tarkman.progress.experiment.push-type.liveactivity` (not the native topic).
  Routes/drain require `SERVICE_PROGRESS_EXPERIMENT_ENABLED` (source accepts trimmed,
  case-insensitive `1/true/yes/on`) AND dedicated 64-hex-character
  `SERVICE_PROGRESS_ENCRYPTION_KEY`; additive migration precedes opt-in. No scheduler
  or recurring heartbeat is installed. Do not “fix” defaults by enabling production.
- A concrete [ApnsProvider](<https://github.com/mattash/Tarkman/blob/46481161509155d04e3fcf60ce7928ea19f9614b/app/services/service_progress/apns_provider.rb>),
  ES256 auth and bounded curl HTTP/2 adapter **already exist**, explicit construction
  only. [DevelopmentBootstrap source](<https://github.com/mattash/Tarkman/blob/46481161509155d04e3fcf60ce7928ea19f9614b/app/services/service_progress/development_bootstrap.rb>)
  separately binds the correct native topic/sandbox, requires literal `enabled:true`,
  `isolated:true`, development Rails environment, one synthetic session, 1–20 explicit
  registration IDs, in-memory 32-byte encryption key and auth or signing configuration;
  1–4 rounds, single-use, no sleep/global drain/scheduler. Synthetic auth/HTTP injection
  exercises it without network. It leaves global outbox signals for normal draining;
  completion counts are not acceptance/display receipts. Secure resource injection
  and physical delivery are not established by this code. Its session/registration
  locks across provider I/O are deliberately bounded feasibility semantics, not a
  production throughput architecture.
- [Backend current guide](<https://github.com/mattash/Tarkman/blob/46481161509155d04e3fcf60ce7928ea19f9614b/docs/service-progress-backend.md>)
  specifies durable fenced revocation, same-second deferred/coalesced publications,
  strictly later actual validation seconds, unchanged retry sequence/expiry and no
  fabricated future clocks. This source-second ordering is already implemented;
  remaining acceptance must validate it, not reopen it from an older native comment.
  Custom sequence alone cannot order stateless terminated
  widget rendering. 429/transient retries are bounded; 5xx's 15-minute retry floor
  exceeds the 60-second payload window, so discard rather than renew/retry early.
