## medium: 401 refresh handling can recurse on the refresh endpoint and stampede concurrent requests

id: fnd_sig-feat-cli-command-ffce3cb9f2-_3355c2cfd2
category: concurrency
confidence: high
triage: confirmed-bug
status: open
feature: Node source app (feat_cli-command_ffce3cb9f2)

evidence:
- app/api.ts:31-42
- app/__tests__/api.test.ts:137-150
- app/__tests__/api.test.ts:225-235

The response interceptor handles every 401 by calling api.post('/refresh-token') through the same axios instance. A 401 from /refresh-token therefore enters the same interceptor with a fresh request config whose _retry flag is unset, so persistent refresh-token 401s can recursively issue more refresh requests instead of immediately clearing auth and redirecting as the test expects. The same block also has no shared in-flight refresh promise or queue, so simultaneous 401s each initiate their own refresh despite the concurrent-401 test documenting the intended single-refresh behavior.

recommendation:
Bypass refresh logic for the refresh endpoint itself and reject/clear auth immediately when it returns 401. Add a module-level refresh promise or request queue so concurrent 401s await one refresh and then retry with the resulting token.

test analysis:
The refresh-failure test only uses replyOnce for /refresh-token, which lets subsequent mock behavior terminate the recursion rather than proving persistent 401 handling. The concurrent test asserts only that localStorage eventually has the refreshed token and explicitly avoids asserting the refresh call count.

suggested regression test:
Add a test where /refresh-token always returns 401 and assert exactly one refresh attempt, token removal, and /login redirect. Add a concurrent 401 test that asserts mock.history.post filtered to /refresh-token has length 1.

minimum fix scope:
Update app/api.ts response interceptor refresh handling and strengthen app/__tests__/api.test.ts around refresh endpoint 401s and concurrent refresh count.

repro:
Configure /protected to return 401 and /refresh-token to always return 401; the refresh request is intercepted as another refreshable 401. Separately, fire three protected requests concurrently with an expired token and observe three /refresh-token calls instead of one.

## medium: Corrupt persisted user data can crash the auth provider

id: fnd_sig-feat-cli-command-afc43aeb3c-_086875acb3
category: bug
confidence: high
triage: confirmed-bug
status: open
feature: Node source app/contexts (feat_cli-command_afc43aeb3c)

evidence:
- app/contexts/AuthContext.tsx:17-23 (AuthProvider)
- app/contexts/__tests__/AuthContext.test.tsx:156-197

AuthProvider parses the persisted `user` value from localStorage without guarding JSON.parse. If localStorage contains malformed JSON, which can happen after manual edits, browser extension interference, an older app version, or partial/corrupt persistence, the effect throws during provider mount and can take down the authenticated app shell instead of clearing the bad auth state. The existing initialization tests cover valid, missing, and empty values, but not malformed persisted user data.

recommendation:
Wrap restore parsing in a try/catch, validate the parsed shape enough for the app's auth contract, and clear `token`/`user` from localStorage when restore fails.

test analysis:
The test suite only verifies valid saved data, missing data, and empty strings; it never stores invalid JSON in `user`.

suggested regression test:
Add an AuthContext initialization test that seeds localStorage with a non-empty token and malformed user JSON, mounts AuthProvider, asserts it does not throw, and asserts auth state/localStorage are cleared.

minimum fix scope:
Update AuthProvider's localStorage restore path and add one malformed-storage regression test.

repro:
Set localStorage `token` to any non-empty value and `user` to `not-json`, then mount AuthProvider. The effect reaches JSON.parse and throws.

## medium: Logout reports success even when server-side sign-out fails

triage: confirmed-bug
status: open
feature: Node source app/api (feat_cli-command_e471ac4105)

- app/api/auth.ts:38-46 (logout)
- app/__tests__/integration/auth.test.tsx:125-132

logout awaits fetch but never checks response.ok or parses an error. Any HTTP 401/403/500 response resolves as a successful Promise<void>, so callers can clear local auth state while the server-side cookie/session may remain valid because the request used credentials: 'include'. test analysis:
The integration test mocks '@/api/auth' entirely, so the real fetch response handling in logout is never exercised. It also asserts only that logout was called, not that failed sign-out responses reject.

suggested regression test:
Add a unit test for logout with fetch mocked to return ok: false and assert that logout rejects with a useful error and does not silently resolve.

minimum fix scope:
Update app/api/auth.ts logout response handling and add focused tests for successful and failed logout fetch responses.

repro:
Have /users/sign_out return HTTP 500 or 401. await logout(token) still resolves, allowing the UI flow to proceed as if sign-out succeeded.
