## medium: Button defaults to submit inside forms

id: fnd_sig-feat-cli-command-2e2938f0fc-_b142d119f0
category: bug
confidence: medium
triage: risk
status: open
feature: Node source app/components/ui (feat_cli-command_2e2938f0fc)

evidence:
- app/components/ui/button.tsx:43-51 (Button)

The shared Button renders a native <button> when asChild is false and forwards props without setting a default type. In HTML, a button inside a form defaults to type="submit", so ordinary action buttons used in forms can submit the form unintentionally unless every caller remembers to pass type="button". Because this is a reusable UI primitive, the impact can appear far from the component definition.

recommendation:
Default the native button case to type="button" while still allowing callers to override with type="submit" or type="reset". Take care not to pass a button-only default through Slot when asChild is true.

test analysis:
No tests are included for these UI primitives, and there is no interaction test covering Button behavior inside a form.

suggested regression test:
Add a React Testing Library test rendering Button inside a form with an onSubmit spy, click it without a type prop, and assert the submit handler is not called; add a second assertion that type="submit" still submits.

minimum fix scope:
Update app/components/ui/button.tsx to apply a default type only for the non-asChild native button render path.

## medium: Integration test script only targets obsolete query-test location

id: fnd_sig-feat-cli-command-4ed2746e64-_d3b3c9e552
category: test-gap
confidence: medium
triage: test-gap
status: open
feature: Node package tarkman-client-refactor (feat_cli-command_4ed2746e64)

evidence:
- package.json:9-11
- AGENTS.md:8-14

The package exposes npm run test:integration as the focused integration suite, but the command only runs app/queries/__tests__/*.integration.test.ts. The review context's linked integration tests are route/auth-oriented and are not under that glob, so the advertised integration command can silently run no relevant integration coverage or miss the actual integration suite. That creates a release risk because contributors may believe integration tests passed when they were not selected.

recommendation:
Update test:integration to match the repository's actual integration test locations, for example a glob covering app/**/__tests__/**/*.integration.test.{ts,tsx} or the concrete app/__tests__/integration and route integration paths.

test analysis:
This is the test selection command itself; tests cannot cover being omitted by the script unless a separate script validation/check is added.

suggested regression test:
Add a small script validation test or CI step that runs npm run test:integration -- --run and fails if Vitest reports no matching test files.

minimum fix scope:
package.json test:integration script

## medium: Raw fetch calls bypass the authenticated API client

id: fnd_sig-feat-cli-command-0c2b709c91-_6ec7f37a36
category: api-contract
confidence: medium
triage: contract-mismatch
status: open
feature: Node source app/queries (feat_cli-command_0c2b709c91)

evidence:
- app/queries/partQueries.ts:12-17 (fetchPart)
- app/queries/sessions.ts:42-73 (fetchSessionParts)
- app/queries/explanationQueries.ts:23-137
- app/queries/__tests__/partQueries.integration.test.ts:29-40
- app/queries/__tests__/sessionQueries.integration.test.ts:20-23

Several query functions construct raw fetch requests instead of using the shared api client used elsewhere in this group. The integration setup logs in and stores a token with the expectation that api.ts will apply it, and session integration also configures the axios api adapter, but raw fetch requests do not receive those auth headers, interceptors, adapter behavior, or any shared response handling. This can make authenticated query endpoints fail in real use even though adjacent mutations and session list calls succeed through api.

recommendation:
Route these requests through the shared api client, or centralize an authenticated fetch helper that applies the same base URL, token, and error behavior as api.ts.

test analysis:
Unit tests mock global.fetch and assert only the URL, so they encode the unauthenticated request shape. The integration tests either skip without credentials or tolerate public endpoint behavior, and they do not assert that Authorization or shared api client behavior is used.

suggested regression test:
Add a unit test for fetchPart or fetchSessionParts that verifies the configured API client/auth path is used after a token is present, or mock the shared client and assert the request goes through it.

minimum fix scope:
Update the raw fetch-based query functions that may require shared auth/config, starting with fetchPart and fetchSessionParts; consider applying the same pattern to explanation query reads for consistency.

## medium: Session part types define incompatible shapes for the same API object

id: fnd_sig-feat-cli-command-18a6ff84d9-_94158246f6
category: api-contract
confidence: medium
triage: contract-mismatch
status: open
feature: Node source app/types (feat_cli-command_18a6ff84d9)

evidence:
- app/types/part.ts:3-20 (Part)
- app/types/session.ts:43-55 (Part)

The project has two exported `Part` interfaces with overlapping domain meaning but different contracts. `app/types/part.ts` allows `ru`, `hy_east`, and `hy_west` to be null and includes fields such as `duration_type`, `page`, `posture`, `sheet_music`, and `assignment`; `app/types/session.ts` makes the same language fields required strings and omits those additional fields. Code typed against the session-local `Part` can therefore treat nullable API fields as always present or silently lose required properties when shared across session/parts flows.

recommendation:
Keep one canonical `Part` interface and import it wherever needed, or explicitly name the session-specific reduced type and derive it with `Pick`/`Omit` so nullability and omitted fields are intentional.

test analysis:
The included auth integration test only exercises login/logout state and does not instantiate or validate session part payload shapes.

suggested regression test:
Add a type-level or runtime fixture test for a session/parts response containing null language fields and the full part metadata, ensuring all consuming types accept the same backend shape.

minimum fix scope:
Unify `Part` definitions across `app/types/part.ts` and `app/types/session.ts`.

## low: Integration auth test is included in the default unit test command but excluded from the integration command

id: fnd_sig-feat-cli-command-18a6ff84d9-_50b45f8076
category: build-release
confidence: high
triage: risk
status: open
feature: Node source app/types (feat_cli-command_18a6ff84d9)

evidence:
- package.json:9-11
- app/__tests__/integration/auth.test.tsx:50-57

`npm run test` excludes only files matching `**/*.integration.test.ts`, while the integration test is named `auth.test.tsx` under `app/__tests__/integration`. That means the default unit test command will run this router/auth integration test, but `npm run test:integration` only targets `app/queries/__tests__/*.integration.test.ts` and will not run it. This makes CI/test selection misleading and can cause integration-only failures to appear in the unit suite while being missed by the integration suite.

recommendation:
Rename the file to an integration-test suffix covered by the scripts and broaden `test:integration` to include `app/__tests__/integration`, or update the default exclusion to skip the integration directory.

test analysis:
This is a test harness configuration issue; the test itself cannot assert which npm script selects it.

suggested regression test:
Add a script-level check or standardize test file naming so integration tests use `*.integration.test.tsx` and are discovered by `npm run test:integration`.

minimum fix scope:
Update `package.json` test globs and/or rename `app/__tests__/integration/auth.test.tsx`.
